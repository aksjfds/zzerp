# v5 模块化单体架构

## 决策

v5 使用模块化单体，而不是立即拆分微服务。所有模块运行在同一 FastAPI
应用和 PostgreSQL 数据库中，因此 QC、库存、生产流动和工单结单仍可保持单事务。

模块之间只能通过 `backend/src/modules/<module>/api.py` 或用途明确的
`*_api.py` 协作。`api.py` 面向 Router 和主要业务用例，`*_api.py` 是为了避免
循环依赖而拆出的窄接口，例如生产操作、只读查询和 QC 路由。模块内部实现文件
不属于公开契约。REST Router 是外部传输边界，不得直接访问 Service、ORM
Model、Repository 或数据库 Session。

## 业务模块

| 模块 | 数据与规则所有权 |
| --- | --- |
| identity | 用户、会话、认证 |
| organization | 部门、车间、工艺 |
| engineering | 产品、版本、BOM、流程图 |
| sales | 客户、客户订单 |
| production_core | 生产项、库存、流动账本、工单编排、操作撤回 |
| standard_execution | 标记、标记集合、计件单价、标准工艺工单 |
| purchasing | 外购入库工单 |
| assembly | 装配工单、装配用料 |
| quality | 送检批次的检验结果和 QC 放行 |
| workforce | 工人维护、加工历史、计件工资 |
| planning | PMC 和跨模块只读投影 |

## 部门模块

`backend/src/departments/` 中的冲压、CNC、表面处理、仓库、装配和 QC
都是独立注册包。部门模块拥有能力声明、权限和表现策略，但不复制生产状态。

- 冲压、CNC、表面处理使用 `standard_execution`。
- 仓库使用 `purchasing`。
- 装配使用 `assembly`。
- QC 使用 `quality`。
- 表面处理额外声明专用打印能力。

动态部门接口先通过 `departments.registry.department_api()` 解析部门模块，
再调用该模块公开方法。

部门门面现在覆盖读取和写入能力：库存、工单、工人维护、标准工艺开单、外购、
装配以及 QC 检验/放行都必须先通过对应部门能力检查。系统管理员执行无法预先
确定部门的全局工单命令时，才直接进入生产核心编排 API。`GET
/department-modules` 提供可检查的部门能力清单。

前端在 `frontend/src/features/departments/` 使用同一组部门模块概念。每个部门
独立声明路由、权限、页面入口和能力，路由表与登录后默认页面从注册表生成。
能力字段实际控制工人和计件价格辅助路由、装配选择逻辑以及表面处理专用打印；
架构测试会校验前后端能力名称和值完全一致。

## 当前迁移状态

本次先建立稳定边界，不改变现有 REST 地址、响应结构、数据库表和生产规则：

1. 各业务模块已有公开 API 和所有权描述。
2. 各生产部门已有独立包、能力描述和统一注册表。
3. HTTP Router 已切换为调用模块 API。
4. 订单状态转换通过生产核心 API 初始化或取消生产。
5. 工单编排通过标准工艺、采购和装配模块 API 分派。
6. 架构测试禁止 Router 绕过模块边界。
7. 前端六个生产部门已通过注册表提供独立页面入口和能力描述。
8. 认证、工程和销售的实现及 Repository 已迁入所属模块。
9. `modules/ownership.py` 为每张 ORM 表声明唯一权威模块，测试确保没有遗漏。
10. 全部后端业务实现已迁入所属模块；模块间调用只能进入公开 API，测试会拒绝
    对其他模块内部文件的直接导入。
11. 跨模块流程通过所有者提供的事务内 `*_api.py` 创建持久化对象；架构测试会
    拒绝模块直接构造其他模块拥有的 ORM 记录，同时校验所有跨模块依赖均已在
    `descriptor.py` 中声明。
12. `modules/read_access.py` 逐表登记当前共享数据库上的跨模块只读访问；新增
    或删除读取都必须同步更新清单，避免 ORM 耦合在无审查的情况下扩散。
13. 架构测试会构建 Python 文件级导入图并拒绝循环依赖。生产撤回命令和工单
    展示之间原有的循环已经拆为独立 `undo_presenters.py`。
14. ORM 类定义已从顶层 `models/` 物理迁入各数据所有者的 `persistence.py`。
    测试确保每张表所在目录与 `modules/ownership.py` 声明完全一致。
15. 跨模块 ORM 读取统一通过数据所有者的 `model_api.py`；顶层 `models/`、
    `services/` 和 `repositories/` 兼容源文件已全部删除，测试禁止这些旧层
    重新出现。
16. 工程模块已把订单引用、生产使用状态、工艺归属和部门编码读取改为所有者
    提供的窄查询 API；组织模块读取工艺标签时也只接收冻结 DTO。这一批跨模块
    ORM 读取授权从 7 项缩减到 1 项，保留项仅用于产品与客户的 ORM 关系和联表
    搜索；该保留项已在后续客户投影改造中清除。
17. 采购模块不再导入部门、工艺、生产项、库存、工单和质检批次 ORM。跨模块
    运行时对象由各所有者的 `context_api.py` 声明稳定结构协议；采购提交后的
    工单状态更新、库存扣减和序列化回到 `production_core.purchase_api` 完成。
    采购模块的跨模块 ORM 读取授权已从 6 项降为 0。
18. 工程产品不再持有销售模块的 `Customer` ORM 关系，只保留数据库外键
    `customer_id`。客户解析返回冻结引用，名称批量查询与客户名搜索由销售模块
    提供标量投影 API；工程模块的跨模块 ORM 读取授权已从最后 1 项降为 0。
19. 质量模块只直接持久化自己拥有的 `WorkOrderBatch`。部门、工人和工艺通过
    不可变引用读取，工单、生产项及 QC 已出货数量通过生产核心的 `qc_api.py`
    获取；质量模块的跨模块 ORM 读取授权已从 6 项降为 0。
20. 人员模块的部门/车间管理、加工历史和计件工资改用组织、生产核心、质量、
    标准工艺及工程模块提供的批量冻结投影。人员模块只直接访问自己拥有的
    `Worker`，跨模块 ORM 读取授权已从 7 项降为 0。
21. 客户订单的产品、BOM 与流程完整性校验由工程模块负责；订单项生产进度和
    生产状态图已迁入生产核心，并通过 `production_core.sales_api` 返回读模型。
    销售模块只持久化客户、订单和订单项，跨模块 ORM 读取授权已从 9 项降为 0。
22. 装配模块只直接持久化装配用料 `WorkOrderMaterial`。库存、生产项和工单
    锁定由 `production_core.assembly_api` 提供，质检批次由质量模块提供，部门
    与工人使用只读引用；工单编号、产出绑定及关闭状态也由生产核心命令修改。
    装配模块的跨模块 ORM 读取授权已从 8 项降为 0。
23. 部门门面已补齐工人维护、标准/外购开单、装配开单和 QC 检验/放行方法；
    HTTP Router 不再直接调用装配、质量或人员模块的部门专属写入用例。
24. 工资计算先从质量模块取得当月合格批次，再批量读取相关标签工单，不再
    扫描工人全部历史工单。装配用料占用也改为一次批量读取，消除了按库存循环
    查询。
25. 测试环境提供默认内存连接配置，普通测试命令不再依赖生产数据库环境变量。
    可选 PostgreSQL 契约测试校验物理表和主键；CI 会加载 `zzerp.sql` 后执行。
26. 每个模块描述符登记 API 版本、主 API 和全部协作 API；架构测试保证清单与
    实际 `*_api.py` 文件一致，避免隐式或无版本边界。
27. 部门门面已从单一共享基类拆为按能力组合的实现；每个部门的 `api.py` 只
    继承自己声明的能力，未声明能力既没有公开方法，也会在注册表解析时返回稳定
    领域错误。
28. 标准工艺模块读取组织、工程、生产核心和质量数据时，已全部改为冻结投影、
    结构协议或所有者事务 API；其跨模块 ORM 读取授权从 11 项降为 0，并由架构
    测试防止回退。
29. PostgreSQL 集成测试覆盖标准工艺开单、送检、检验、放行、装配、最终 QC
    和客户订单结单，并验证失败的订单创建不会留下部分数据；CI 使用基线 SQL
    初始化一次性数据库后执行。

现有业务实现、Repository 和 ORM 定义均位于所属模块。新代码只能选择公开业务
API、事务所有者 API、所有者提供的只读投影 API、登记过的只读 `model_api.py`
或模块内部实现，不再存在可绕回的旧 Service、Repository 和 Model 入口。

模块化单体阶段仍允许跨模块只读查询和共享同一个 SQLAlchemy Session，以保证
复杂生产流程的查询效率和事务原子性；但新建持久化记录必须进入数据所有者 API。
新增跨模块查询应优先返回标量、字典、Pydantic 契约或冻结 DTO；只有确实需要
SQLAlchemy 关系映射或高性能联表投影时，才能登记新的 `model_api.py` 读取授权。
同一事务内必须传递运行时对象时，使用不依赖 SQLAlchemy 的 `context_api.py`
结构协议，并把状态修改留在数据所有者的命令 API。架构测试会确保这些上下文
协议不导入数据库或持久化实现。
事务内 `context_api.py` 协议和 owner command API 可能由当前 SQLAlchemy
对象实现，它们不是可直接暴露到网络的接口。如果未来拆为独立服务，应在这些
边界外新增可序列化的命令、DTO 和领域事件，而不是传输 ORM 对象。

## 已知共享读取边界

以下读取属于明确登记的共享数据库投影，不被描述为已经解耦：

| 模块 | 外部表授权数 | 原因与收敛方式 |
| --- | ---: | --- |
| `planning` | 15 | PMC 跨域报表；长期迁移为批量投影或独立只读模型 |
| `production_core` | 13 | 生产状态机的高性能库存/工单联表与事务编排 |

包括 `standard_execution` 在内的其他业务模块，其外部 ORM 读取授权均为零。
任何数量变化都必须同时修改
`modules/read_access.py` 并通过架构测试。这里的目标不是为了数字归零而复制
数据或拆散事务；当查询能够由数据所有者批量返回稳定投影且不造成明显性能退化
时，再删除对应授权。

持久化模型的权威位置为：

- `identity/persistence.py`：用户和会话。
- `sales/persistence.py`：客户、订单和订单明细。
- `engineering/persistence.py`：产品、版本、BOM 和流程。
- `organization/persistence.py`：部门、车间和工艺。
- `workforce/persistence.py`：工人。
- `production_core/persistence.py`：生产项、库存、工单、流动和撤回记录。
- `standard_execution/persistence.py`：标签、组合、价格、标签库存和计件明细。
- `assembly/persistence.py`：装配用料。
- `quality/persistence.py`：送检批次。

## 前端构建边界

部门页面继续按路由动态加载。生产构建进一步把 Vue、Element Plus、LogicFlow
和其他第三方依赖拆成独立缓存块，避免某个部门或工程页面把公共依赖合并进单个
超大业务包。拆包规则位于 `frontend/vite.config.ts`，当前最大 JavaScript
产物已从约 866 KB 降至约 116 KB。

## 后续拆分服务的条件

只有在某模块出现独立发布、独立扩容、独立安全域或独立团队的实际需求时，
才将其进程内 API 替换成 HTTP 或消息适配器。在此之前不允许通过共享数据库
模拟微服务。

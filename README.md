# zzerp v6

zzerp MES 是基于 FastAPI、PostgreSQL 和 Vue 的模块化应用，保留工程产品外观版本、
BOM、流程图与统一生产计划。创建产品或新增外观版本时可填写版本值（如 V1、金色、亮银或纯数字），长度1–100，同产品内不重复；页面原样显示，不自动拼接V。同一产品的各外观版本分别维护独立 BOM 和流程图，产品基础信息共用。创建计划填写客户和唯一订单号，可选择多个该客户的产品，
每个产品分别填写订单数量和生产数量，并选择复制来源外观版本；保存时生成独立的产品资料、BOM 和正式流程快照，之后不再跟随工程版本。确认计划时任一产品生成失败则整单回滚。
流程图由配件节点和部门节点组成，连线表达路线。保存草稿记录订单、产品快照和快照路线依据；确认计划时才按快照路线生成部门工单；撤回确认要求无流水并移除工单，未确认计划不进入生产进度或部门工单；
普通配件按生产数量乘 BOM 用量安排，激光/装配汇合后的装配体按生产数量安排并自动命名。
九个生产部门使用独立账号，只能查看和操作各自工单；内部出料生成交接票，下游每票仅可登记一次实际到料；数量不得超过票面出料，少到料须备注且差额不可补录；冲压部和外购部无需到料，直接出料；其他本部门工单可登记无来源到料，但备注必填。登记时不选择关联到料，除冲压/外购豁免外，本次出料大于部门停留数量时必须备注，有备注允许超额；普通配件停留数量按到料减出料，装配体按BOM齐套数减出料，不自动转入下游。装配体到料按实际物料分项。已有流水不可删除，计划不能再重建工单。新增配件自动填写厂编加递增后缀。计划产品快照保留创建时的配件、用量与路线，工程修改不影响已有计划。后端模块通过公开 API 协作。
生产账号用户名为部门代码（stamp、cnc、grinding、outsource、vibration、laser、assembly、purchase、finished），
开发基线初始密码沿用 1。工单范围由后端按认证部门强制限定，工程/业务账号保留原权限。

## AI 与 Agent 项目原则

稳定 + 规范 + 低耦合 + 尽量无性能损失。

所有修改必须基于当前真实代码和实际问题，优先采用可回退、可验证、职责边界
清晰的实现；不得为了局部性能提升破坏稳定性、正确性、兼容性或代码结构。

## 数据库职责

`zzerp.sql` 是开发阶段唯一的破坏性重建基线，负责表结构、关系约束、必要的
并发完整性底线以及初始化数据。SQLAlchemy ORM 必须与其保持一致，但不作为
第二套结构来源。完整业务状态转换由后端领域模块负责，不在数据库触发器中
重复实现。

数据库函数不解析流程图或选择节点。数据库保留关系、数量与格式约束，
部门页面的“部门流水”可分页查看本部门全部工单流水，按秒级时间从早到晚排列。交接票仅允许一次到料登记；本次数量小于票面时必须填写备注，登记后差额不再允许补录。

激光部、装配部的装配体工单以树形显示各配件，可逐件登记无来源到料和查看到料流水；装配体统一登记出料，整套到料保留在一级全部流水。

业务“生产进度查看”按订单分页，每个订单一张独立的产品→配件/装配体→部门工单三级树表，表内无订单号列，表外标题显示订单。可筛选订单/产品并查看流水，路线及数量按订单独立，三级默认收起。生产账号仍使用所属部门操作页。

手机端筛选纵向排列，宽表在表格区域横向滑动；窄屏操作列随表格滚动。工程流程节点可触屏点击添加，画布空白处可单指平移，缩放使用画布工具按钮；桌面仍支持鼠标拖拽与框选。

触发器维护通用更新时间、流水不可变及已登记工单来源保护；流程图结构、节点引用及可达关系由后端统一校验。

初始化数据分为系统必需基础数据和可删除开发示例数据；数据库重建由用户执行。外观版本记录保存自定义显示值，计划快照独立保存来源版本显示值。现存数据库需先同步版本字段、快照字段及 `plan_product_route` 表，不能直接沿用旧结构，也不能把当前工程资料当作历史原始快照。

## 网页风格

全站采用 StyleKit「企业简洁风」（corporate-clean），以权限侧栏、统一顶栏和业务工作区组织页面。登录分岗位入口，产品与计划提供真实范围概览，工程编辑按资料/BOM/工艺章节组织，生产工单和流水在页内切换。应用外壳位于 `frontend/src/layouts`，公共标题和图标保持纯展示职责。色彩、字体、圆角及阴影集中在 `frontend/src/shared/theme`，流程图共用同一主题；动效位于 `frontend/src/shared/motion`。数据表和工程画布保留宽工作区，窄屏在表格内部横向滚动。现行要求见 [界面规范](openspec/specs/interface-theme/spec.md)。

## 开发环境

```bash
python3 -m pip install -r backend/requirements.txt
pnpm --dir frontend install
pnpm run check
```

`pnpm run check` 会执行后端架构一致性检查、前端类型检查和生产构建。后端检查会在不连接数据库的前提下核对应用导入、表所有权、模块公开接口、未声明依赖、循环与局部导入、SQL/ORM 的表/字段/约束/索引名称，以及前端 shared 和 feature 导入边界。AI 或 Agent 默认只做代码规范、模块耦合和稳定性审查；只有用户当前请求明确要求时才执行构建或项目脚本。

AI 或 Agent 只有在用户当前请求明确授权后才能执行安装、构建、项目脚本或数据库操作；具体限制以 `AGENTS.md` 为准。

## Docker 开发

```bash
docker compose up -d --build app
docker exec -it app bash
pnpm f
```

Compose 会为容器创建独立的 `frontend/node_modules` 数据卷，并按照容器的
Linux 架构自动安装锁文件中的依赖。不要把宿主机的 `node_modules` 直接共享给
容器；Vite/Rolldown 等工具包含平台相关的原生二进制。开发镜像固定使用
Python 3.12 和 Node 22，并在构建阶段安装 `backend/requirements.txt`；
后端依赖变更后再次执行带 `--build` 的启动命令即可。
